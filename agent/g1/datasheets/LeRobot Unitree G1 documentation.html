Unitree G1

The Unitree G1 humanoid is supported in LeRobot. You can teleoperate, train locomanipulation policies, test in simulation, and more. Both 29 and 23 DoF variants are supported.

Embodiment Selection

One UnitreeG1 class selects its joint definitions through UnitreeG1Config.embodiment. The default is g1_29; existing configurations therefore retain G1-29 behavior. Select the 23-DoF layout with --robot.embodiment=g1_23 or in Python:

from lerobot.robots.unitree_g1 import UnitreeG1Config

config = UnitreeG1Config(embodiment="g1_23", is_simulation=False)
CapabilityG1-29G1-23
Joint configuration and action/observation features29 body joints, 14 arm joints23 body joints, 10 arm joints
DDS command/feedback layout29 active slots29 slots with absent joints left inactive
MuJoCo simulationSupportedNot yet supported; native model planned
Locomotion controllersGR00T and HolosomaGR00T and Holosoma
SONIC whole-body controllerSupportedNot supported; the policy requires 29 DoF
Gravity compensationSupported, off by defaultNot yet supported; native kinematics planned

Both variants use the same 29-slot DDS message layout. G1-29 uses all 29 slots, while G1-23 uses 23 and leaves the six nonexistent-joint slots inactive. The kp, kd, and default_positions vectors therefore remain 29 elements long and are indexed by DDS slot. G1-23’s active arm slots are 15..19 and 22..26. Slots 13, 14, 20, 21, 27, 28 have no active joint; their config values must be zero. They are omitted from action/observation features, not renumbered. Inactive and reserved command entries are cleared before publishing a G1-23 message. Explicit gain overrides must be finite, nonnegative, and use the same sparse layout. Default gains are shared by joint name across both variants, so identical physical joints use identical gains while absent G1-23 slots remain zero.

Native G1-23 MuJoCo simulation is not supported yet. Selecting the G1-23 embodiment with simulation enabled fails before transport initialization. A native G1-23 MuJoCo model is planned for a future version.

Part 1: Getting Started

Install the Unitree SDK

Follow the unitree_sdk2_python installation guide. Tested with unitree_sdk2py==1.0.1 and cyclonedds==0.10.2:

conda create -y -n lerobot python=3.12
conda activate lerobot
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
pip install -e .
cd ..

Install LeRobot

conda install ffmpeg -c conda-forge
conda install -c conda-forge "pinocchio>=3.0.0,<4.0.0"
git clone https://github.com/huggingface/lerobot.git
cd lerobot
pip install -e '.[unitree_g1]'
For now, pinocchio must be installed from conda-forge (not pip) to include the CasADi bindings needed for arm IK.

Test the Installation (Simulation)

The simulation environment has its own dependencies. Check the Simulation environment dependencies: Unitree G1 Mujoco EnvHub.

pip install mujoco loguru msgpack msgpack-numpy
lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --teleop.type=unitree_g1 \
  --teleop.id=wbc_unitree \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 5}}' \
  --display_data=true \
  --robot.controller=GrootLocomotionController

This will launch a MuJoCo sim instance for the G1. You can connect a gamepad to your machine before launching in order to control the robot’s locomotion in sim. We support both HolosomaLocomotionController and GrootLocomotionController via --robot.controller.

  • Press 9 to release the robot
  • Press 7 / 8 to increase / decrease waist height

Choosing the End Effector

--robot.end_effector says what the arms carry: dex1 for the parallel grippers (the default), dex3 for the three-finger hands, or dummy for bare wrists. In simulation it picks the MuJoCo model, which decides the finger actuators and which cameras the scene carries — the wrist cameras are mounted on the end effector, so dummy only has head_camera.

lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.end_effector=dex3 \
  --teleop.id=wbc_unitree \
  --robot.controller=GrootLocomotionController

The sim publishes the model’s cameras over ZMQ on --robot.sim_camera_port (5555 by default), which is where the zmq cameras in --robot.cameras read them from. Pass --robot.sim_publish_images=false to open MuJoCo’s interactive window instead: the sim renders either its cameras or its window, never both, since the offscreen contexts belong to the thread that creates them rather than to the viewer’s. --robot.sim_onscreen names that choice outright rather than leaving it to the cameras, and asking for both is refused; set it and --robot.sim_publish_images both false to render neither, which is what a machine with no display can do.

Connect to the Physical Robot

The G1’s Ethernet IP is fixed at 192.168.123.164. Your machine must have a static IP on the same subnet: 192.168.123.x where x ≠ 164.

# Replace 'enp131s0' with your ethernet interface name (check with `ip a`)
sudo ip addr flush dev enp131s0
sudo ip addr add 192.168.123.200/24 dev enp131s0
sudo ip link set enp131s0 up

SSH into the Robot

ssh unitree@192.168.123.164
# Password: 123

Share Internet via Ethernet

The G1 needs internet access to clone repos and install packages. Share your laptop’s connection over Ethernet:

On your laptop:

sudo sysctl -w net.ipv4.ip_forward=1

# Replace wlp132s0f0 with your WiFi interface name
sudo iptables -t nat -A POSTROUTING -o wlp132s0f0 -s 192.168.123.0/24 -j MASQUERADE
sudo iptables -A FORWARD -i wlp132s0f0 -o enp131s0 -m state --state RELATED,ESTABLISHED -j ACCEPT
sudo iptables -A FORWARD -i enp131s0 -o wlp132s0f0 -j ACCEPT

On the G1:

sudo ip route del default 2>/dev/null || true
sudo ip route add default via 192.168.123.200 dev eth0
echo "nameserver 8.8.8.8" | sudo tee /etc/resolv.conf

# Verify
ping -c 3 8.8.8.8

Install the Unitree SDK on the G1

Follow the unitree_sdk2_python installation guide:

conda create -y -n lerobot python=3.12
conda activate lerobot
git clone https://github.com/unitreerobotics/unitree_sdk2_python.git
cd unitree_sdk2_python
python -m pip install -e .
cd ..

Install LeRobot on the G1

git clone https://github.com/huggingface/lerobot.git
cd lerobot
conda install -c conda-forge "pinocchio>=3.0.0,<4.0.0"
python -m pip install -e '.[unitree_g1]'
For now, pinocchio must be installed from conda-forge (not pip) to include the CasADi bindings needed for arm IK.

(Optional) Enable WiFi on the Robot

For wireless SSH access, you can enable WiFi on the G1 (it’s blocked by default):

sudo rfkill unblock all
sudo ip link set wlan0 up
sudo nmcli radio wifi on
sudo nmcli device set wlan0 managed yes
sudo systemctl restart NetworkManager

Connect to a WiFi network:

nmcli device wifi list

sudo nmcli connection add type wifi ifname wlan0 con-name "YourNetwork" ssid "YourNetwork"
sudo nmcli connection modify "YourNetwork" wifi-sec.key-mgmt wpa-psk
sudo nmcli connection modify "YourNetwork" wifi-sec.psk "YourPassword"
sudo nmcli connection modify "YourNetwork" connection.autoconnect yes
sudo nmcli connection up "YourNetwork"

ip a show wlan0

You can then SSH over WiFi instead of Ethernet:

ssh unitree@<ROBOT_WIFI_IP>
# Password: 123

Part 2: Teleoperation & Locomotion

Run the Robot Server

On the robot (from ~/lerobot):

cd ~/lerobot
python src/lerobot/robots/unitree_g1/run_g1_server.py --camera

Run the Locomotion Policy

You can run the teleoperation client from your laptop over Ethernet, over WiFi (experimental), or directly on the robot itself. Mind potential latency introduced by your network.

From your laptop:

lerobot-teleoperate \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.robot_ip=<ROBOT_IP> \
  --teleop.type=unitree_g1 \
  --teleop.id=wbc_unitree \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "<ROBOT_IP>", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --display_data=true \
  --robot.controller=HolosomaLocomotionController

We support both GrootLocomotionController and HolosomaLocomotionController via --robot.controller.

Part 3: Loco-Manipulation with the Homunculus Exoskeleton

We provide a loco-manipulation solution via the Homunculus Exoskeleton — an open-source 7 DoF exoskeleton for whole-body control. Check it out here.

Calibrate

lerobot-calibrate \
  --teleop.type=unitree_g1 \
  --teleop.left_arm_config.port=/dev/ttyACM1 \
  --teleop.right_arm_config.port=/dev/ttyACM0 \
  --teleop.id=exo

During calibration move each joint through its entire range. After fitting, move the joint in a neutral position and press n to advance.

Record a Dataset

lerobot-record \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --teleop.type=unitree_g1 \
  --teleop.left_arm_config.port=/dev/ttyACM1 \
  --teleop.right_arm_config.port=/dev/ttyACM0 \
  --teleop.id=exo \
  --dataset.repo_id=your-username/dataset-name \
  --dataset.single_task="Test" \
  --dataset.num_episodes=2 \
  --dataset.episode_time_s=5 \
  --dataset.reset_time_s=5 \
  --dataset.push_to_hub=true \
  --dataset.streaming_encoding=true \
  --dataset.encoder_threads=2

Note: Omit --teleop.left_arm_config.port and --teleop.right_arm_config.port if you’re only using the joystick.

Example dataset: nepyope/unitree_box_move_blue_full

Part 4: Training & Inference

Train

python src/lerobot/scripts/lerobot_train.py \
  --dataset.repo_id=your-username/dataset-name  \
  --policy.type=pi05 \
  --output_dir=./outputs/pi05_training \
  --job_name=pi05_training \
  --policy.repo_id=your-username/your-repo-id \
  --policy.pretrained_path=lerobot/pi05_base \
  --policy.compile_model=true \
  --policy.gradient_checkpointing=true \
  --trackio.enable=true \
  --policy.dtype=bfloat16 \
  --policy.freeze_vision_encoder=false \
  --policy.train_expert_only=false \
  --steps=3000 \
  --policy.device=cuda \
  --batch_size=32

Inference with RTC

A compatible trained policy can use local inference-time RTC:

lerobot-rollout \
  --strategy.type=base \
  --policy.path=your-username/your-repo-id \
  --policy.device=cuda \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.controller=HolosomaLocomotionController \
  --robot.cameras='{"global_view": {"type": "zmq", "server_address": "<ROBOT_IP>", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30}}' \
  --task="task_description" \
  --duration=1000 \
  --fps=30 \
  --inference.type=rtc

G1 locomotion controllers do not declare the retained-target contract used by rollout’s recoverable waiting. After motion begins, exhausting their action buffer therefore causes a terminal fault rather than a grace-period wait. Request deadlines and observation-age limits also apply. Validate that the policy’s usable chunk covers inference latency before using this recipe; see local RTC waiting and budgets. SONIC has a separate retained-token contract described below.

Part 5: SONIC Whole-Body Control (Latent-Token Policies)

LeRobot now ports the decoder half of NVIDIA’s SONIC whole-body deploy stack as the SonicWholeBodyController. Instead of commanding joints, the policy outputs a 64-D latent motion token (motion_token.{i}.pos) each tick; the SONIC decoder maps that token plus recent proprioception history onto a residual action that is scaled and added to the standing pose, producing 50 Hz joint-position targets for all 29 DoF.

The controller loads its ONNX decoder and all deploy constants (PD gains, default_angles, action_scale, and the neutral token) from lerobot/sonic_decoder. The repo also ships a distilled low-latency decoder, selectable with the controller’s policy_type="low_latency" argument (defaults to "default").

Test in Simulation

Any token-output policy trained on SONIC motion tokens (e.g. nepyope/sonic_walk) can drive it:

lerobot-rollout \
  --strategy.type=base \
  --policy.path=nepyope/sonic_walk \
  --policy.device=cuda \
  --robot.type=unitree_g1 \
  --robot.is_simulation=true \
  --robot.controller=SonicWholeBodyController \
  --robot.cameras='{"ego_view": {"type": "zmq", "server_address": "localhost", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 15}}'

Run on the Physical Robot

Run the remote inference policy server on the GPU machine and keep the robot bridge, SONIC decoder and rollout client on the G1 Jetson. Only 64-D token chunks cross the network; the decoder and 50 Hz rt/lowcmd loop remain onboard.

Install the remote extra on both machines. Keep the Unitree extra on the G1:

# GPU machine
python -m pip install -e '.[remote]'

# G1 Jetson
python -m pip install -e '.[unitree_g1,remote]'

On the GPU machine, start the policy server from the repository root. The maintained profile matches nepyope/sonic_walk; copy and update its checkpoint and feature contract together for another policy.

lerobot-policy-server \
  --config_path=examples/remote_inference/unitree_g1_sonic.yaml

On the G1, keep the bridge and camera running:

python src/lerobot/robots/unitree_g1/run_g1_server.py --camera

Then start the rollout client in a second G1 terminal, replacing <GPU_MACHINE_IP>:

lerobot-rollout \
  --strategy.type=base \
  --inference.type=remote \
  --inference.endpoint=tcp/<GPU_MACHINE_IP>:7447 \
  --inference.deployment=g1-sonic \
  --inference.semantics=unitree-g1-sonic-motion-token-v1 \
  --inference.encoding=jpeg \
  --inference.action_starvation_grace_s=1.0 \
  --robot.type=unitree_g1 \
  --robot.is_simulation=false \
  --robot.robot_ip=127.0.0.1 \
  --robot.controller=SonicWholeBodyController \
  --robot.cameras='{"ego_view": {"type": "zmq", "server_address": "127.0.0.1", "port": 5555, "camera_name": "head_camera", "width": 640, "height": 480, "fps": 30, "warmup_s": 5}}' \
  --task='walk forward' \
  --fps=30 \
  --return_to_initial_position=false \
  --interactive=true

Type /start only after the G1 is clear to move. SONIC declares waiting support because re-sending the last complete token keeps the onboard decoder balancing. Before the first policy result, rollout sends the decoder’s neutral token. If the action buffer runs dry, it repeats the last applied token for at most action_starvation_grace_s (one second above); if no fresh prediction arrives, rollout faults and follows its configured shutdown/disconnect path. G1 locomotion controllers remain unsupported because their joystick velocities cannot be retained this way.

The recipe disables return-to-initial-position: interpolating through SONIC’s latent-token space is not a validated physical homing trajectory. Avoid /reset for the same reason, since it would sweep the token back to its connect-time value. /stop still closes the remote session and disconnects the robot through the normal controller shutdown path.

With SonicWholeBodyController, the observation state is the 64-D token echo rather than the 29 joint positions, so a compatible checkpoint must be trained against that state. On connect, the robot eases joints to the decoder’s default_angles before the controller takes over.
